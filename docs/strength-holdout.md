# 実日報ホールドアウト評価

GitHub #18（評価の仕組み）と #3（実データでの評価）に対応する。実日報20件、各2名の独立ラベル、部分一致以上80%・受容率80%を暫定基準とする。未評価を合格扱いしない。

## 手順と記録

1. 評価責任者が、実日報であり評価者が解析結果を見ていないことを確認する。専用の評価環境で自動解析を停止し、本人の提出済み日報を選ぶ。シード・生成した日報は対象外。
2. 日報IDから評価ケースを作り、原文・材料版・SHA-256・作成者と日時を固定する。同じ日報の重複登録は拒否する。後の日報編集で材料を変えない。
3. 異なる講師アカウント2名が、互いのラベルやモデル出力を見ずにスキルコード（該当なし可）と理由を確定する。結果未閲覧の申告が必要。確定後の変更、同じ人の2票目、3名目を拒否する。
4. 2名の確定後に凍結した材料を解析し、その材料のハッシュを付けて結果を登録する。解析担当者には画面の「解析担当者向けの凍結材料JSON」だけを渡し、人間ラベル・受容性・他モデルの結果を解析入力に含めない。provider/model/promptVersionを実際の実行条件として記録する。既存の強み結果と同じスキル・原文引用検証を通す。結果は1度だけ固定し、利用者への強み・課題配信には使わない。
5. 各評価者が結果を閲覧して受容性と理由を記録する。ラベルは変更しない。受容性も1度だけ固定する。
6. 両名の受容性まで揃ったケースだけを集計する。コード集合の完全一致/共通あり/共通なしを計算し、20ケース以上かつ40票以上で暫定基準を判定する。旧方式の評価は参考件数として表示し、合格判定から除く。最新の評価ケース番号に登録されたprovider/model/promptVersionと同じ実行条件だけを集計し、異なるモデルやプロンプト版を混ぜない。

!NOTE: システムは別アカウントと操作順序を保証するが、同一人物による複数アカウントの使用、画面外での出力閲覧、実日報かどうかまでは証明できない。責任者が評価者・データの由来・未閲覧を確認する。評価者はラベル確定前に通常の解析管理・本人の強み画面を閲覧しない。

## 判断とHITL

- 件数不足: 未合格。実日報と評価者を追加する。
- 基準未達: 誤判定と引用を講師が確認し、プロンプトや判定規則を改善する。既存ラベルを書き換えず、新しい未閲覧の日報で再評価する。
- 基準到達: この評価集合での暫定目安達成。教育効果や新しい職種への一般化は別途検証する。
- 強み・課題案の本人配信は引き続き講師承認が必須。根拠不足、引用不一致、処理失敗は配信せず講師へ戻す。評価合格によって承認を省略しない。
