# 能力・性格傾向としての強み解析

## 目的

作業の一覧ではなく、複数の記録に表れた「何が得意か」「どのような仕事の進め方をするか」を本人が理解できるようにする。短い能力・傾向の見出し、判断した理由、原文の根拠、評価できる範囲、次の取り組みを表示する。

## 解析結果

既存の強み候補に次の解釈を追加する。

- `kind`: `ability`（得意な能力）または `work_style`（性格・仕事の進め方の傾向）。旧結果は `ability` として表示する。
- `label`: 再利用できる能力・傾向を短く表す。「一覧スクリプトを作成」等の作業名ではなく、「ソースコードを整理して実装するのが得意」「慎重に確かめるタイプ」等の粒度とする。これらは表現例であり、対象者にあらかじめ付ける正解ではない。
- `summary`: 具体的な作業から能力・傾向へどう解釈したかを説明する。
- `scopeNote`: 観測できた状況と評価の限界を記す。
- `skillCode`, `confidence`, `evidence`, `growthAction`: 現在の契約を保持する。

性格傾向の候補は、少なくとも異なる2件の日報・課題からの本人の達成根拠を必要とする。同一提出の回答と講師コメントを2回の観測として数えない。原文引用の一致を検証し、Problem・Try・感情・未実施・伝聞を達成の証拠へ転用しない。

!NOTE: 「性格」は仕事で観測した傾向として扱う。固定的な人格、診断、本人の内面や意欲を記録なしに断定しない。根拠が足りなければ傾向を空にし、何を追加観測するとよいかを説明する。AI代替PoCはAIの行動を評価したものと表示する。

## 保存・承認

既存DBの候補列を破壊しない追加テーブルで解釈を保存する。候補識別と承認済み結果の置換は `kind` と `skillCode` の組で行い、同じ領域の能力と性格傾向を両立させる。旧形式は能力として扱い、新形式の能力承認で旧候補を置換できる。

講師は見出し・解釈・範囲・育成アクションを確認して承認する。本人・ホームへの表示は引き続き承認済みに限定する。新しい解釈が承認されるまでは古い承認済み候補を保持する。

## 可視化

強み画面に「得意な能力」「性格・仕事の進め方の傾向」の2つのまとまりを設ける。各カードは見出し・解釈・範囲・次の取り組みを表示する。本人向けの「根拠を見る」は2026-09-30のユーザー指示で一時凍結し、引用ログ・材料ID・出典・スキルコードの展開欄を描画しない。講師は承認のために引き続き根拠を確認できる。根拠の保存・検証・API契約は維持する。

ホームも能力と仕事の進め方を区別し、短い要約タグだけを表示する。判断理由は詳細画面へ集約する。SFIAコードや内部ジョブIDは本人の主表示には使わない。AI作業PoCの出典表示はタグ内に残す。言い換えと旧形式の扱いは [ホーム仕様](screens/home.md#要約タグの表現) を参照。

!NOTE: 原文ログをそのまま本人へ提示する状態では読み解く負担が大きいため、本人向け根拠表示を凍結した。再開時には本人が理解できる説明への整理を検討する。講師の確認と保存データは凍結対象に含めない。

## 今回の実行

この改善を竹内の新しい課題として配信し、実装・検証の成果物を提出した。作業者が日報を作成して提出し、管理職・講師・シニアエンジニアが日報のみを独立にレビューした。Fan-inと要約を保存し、独立モデルが既存3課題と今回の提出を含む材料から新契約で解析した。AI講師としての確認と本人の画面検証まで完了した。[実行結果](poc-strength-profile-2026-09-29.md)を参照。

## 追加テスト観点

1. 能力・性格傾向・理由・範囲・根拠を保存し、承認後に本人画面とホームへ反映できる。
2. 性格傾向には異なる2記録の本人根拠が必要で、講師コメントだけ・同一提出の重複・引用不一致・文脈専用項目を拒否する。
3. 旧形式・既存DBを保持し、能力と性格傾向が互いを消さず、同種の新しい承認だけが旧結果を置換する。
4. 能力と性格傾向を別に表示し、講師の根拠の開閉・編集と承認・空状態・狭い画面の表示が機能する。

2026-09-29にユーザー承認済み。[テスト観点](test-perspectives.md)のSP-1〜4へ対応付ける。既存の本人分離・未承認非表示・古いジョブ拒否の観点も維持する。
