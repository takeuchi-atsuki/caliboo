# GUI応答時間改善 (#26)

本書の前半は初回改修（`8c99b70`）時の結果を保存したものである。頻用ルートの初回遷移を見直した追補と、25ブラウザセッションの比較結果は末尾を参照する。

## 目的・比較条件

データ件数が増えるときに不要なSQLが増える箇所と、初回のJavaScript転送量を減らす。
改修前の比較元は `bbddd81b766fb0ed37f90eb41b98bfdd54d21c5c`（#24取込後）。
今回はキャッシュではなくルート単位の遅延読込と読み取りの一括化を先に検証する。

- 24名のメンバーと1名の講師を模した25名の架空アカウント。実在する人物・業務資料・運用DBは使用しない。
- 比較元と改修後の依存バージョン、端末・ブラウザ条件、データ規模、操作順を揃える。別チェックアウト・別SQLiteにする。
- 外部有料サービスを使わないためAI providerは `manual`。ネットワークを必要としない計測を先に実施する。
- APIのp50/p95、SQL件数（認証を含む）、エラー、レスポンス内容、初回JS gzip合計を記録する。
- GUIはログイン、ホーム、強み、課題一覧の通常閲覧・講師の承認確認を対象とする。キャッシュを空にした初回と再訪を区別する。
- 同時25人の実際の利用感を比較する場合は、同一PC/DB条件のローカル検証環境で各参加者が通常の操作を行う。同時接続・通信を自動大量生成する負荷ツールは使用しない。

## 本番ビルドの初期JS量（初回改修）

両チェックアウトで同じlockfileの依存を用い、フロントエンドで正式ビルドを実行する。

```sh
cd frontend
npm run build
node scripts/measure-initial-js.mjs
```

改修前には計測スクリプトがないため、改修後のスクリプトから比較元の正式ビルド済み `dist` を指定する。

```sh
node scripts/measure-initial-js.mjs /独立した比較元/frontend/dist
```

各JSファイルを個別にgzip圧縮し、HTMLのmodule entry・modulepreloadと静的import/exportの依存閉包を重複除外してバイト数を合計する。画面の動的importが必要なシナリオはその依存閉包も加える。独立したモデル閲覧ページ、CSS、画像、訪問していないページの遅延chunkは初回JS量に含めない。

| シナリオ | 改修前（B） | 改修後（B） | 削減率 |
|---|---:|---:|---:|
| 初期HTMLが要求するJS | 190,719 | 89,845 | 52.89% |
| 初回ログイン画面 | 190,719 | 107,486 | 43.64% |
| 認証済み状態で初回ホーム | 190,719 | 127,907 | 32.93% |
| ログインからホームまで（重複排除） | 190,719 | 129,966 | 31.85% |

削減率は `(改修前 - 改修後) / 改修前 × 100`。初回ログイン→ホームでも目標の15%以上を達成した。

> [!NOTE]
> この値は正規ビルドから算出したgzipバイト数であり、実回線の転送時間・レンダリング時間ではない。遅延読込によって初めて訪れる画面で追加のchunk取得は発生する。

## 25名分の合成データでAPIを比較する

`devel/measure_gui_api.py` を利用する。開発用依存（backendの `[dev]`）をインストールした同じPythonで実行する。
DBはプロファイルごとに自動生成・後片付けする一時SQLiteで、入力する既存DBファイルやサーバーURLはない。起動環境から引き継いだDB接続設定も破棄する。アプリ内 `TestClient` だけを使用し、TCP/IP接続を遮断する。

```sh
# 改修後のチェックアウトのルートにて実行
PYTHONPATH=/独立した比較元/backend/src python3 devel/measure_gui_api.py > before.json
PYTHONPATH="$PWD/backend/src" python3 devel/measure_gui_api.py > after.json
```

依存ライブラリはPython環境にインストールしたものを使う。比較元のソースを上のように明示することで、計測スクリプト自体は前後で同一に保つ。`--profile small` または `--profile populated` で片方だけ実行することも可能。

| 合成データ | small | populated |
|---|---:|---:|
| 利用者 | 25（メンバー24、講師1） | 25（メンバー24、講師1） |
| メンバーごとの日報 | 3 | 24 |
| メンバーごとの強みジョブ | 2 | 10 |
| 全員課題/個人宛て課題（1人あたり） | 6 / 2 | 36 / 12 |
| 課題全体 | 54 | 324 |
| メンバー本人に見える課題 | 8 | 48 |

各ユーザーは正式なログインAPIから個別のセッションCookieを取得する。
メンバー24人についてホーム・強み・学習行動・課題一覧を2回ずつ、講師は処理待ちジョブ一覧を2回、各メンバーの強みを2回ずつ閲覧する。測定前に一度ウォームアップし、閲覧の間隔を空ける。SQLAlchemyのイベントでリクエストごとにSQLを計数し、クライアント往復時間とサーバー処理時間を記録する。p50は中央値、p95はnearest-rank方式。エラー応答なら失敗として実行を停止する。
一括化により戻り値が変わっていないことを検証するため、各APIで全測定レスポンスのJSON（キー順固定）をSHA-256で記録する。課題については本人に見える件数・配信先も検証する。

> [!NOTE]
> これは25人分の独立したログインセッションで通常閲覧を順番に再現するAPI計測で、25人同時利用・ブラウザ描画・5秒ポーリング・日報提出などの書き込み負荷を測定したものではない。講師のジョブ一覧はサンプル2件のみなのでp95を参考値として扱う。絶対時間は端末やバックグラウンド処理に依存する。SQL件数とレスポンス一致は再計測でも特に確認する。

## 同時25人の通常業務を手動で比較する手順（未実施）

この手順は実際の利用感を測る追加検証用であり、上記の逐次API計測とは別である。
ローカルの独立した検証環境で同じデータをブラウザから扱うため、前後それぞれのバックエンドソースを指定して、次を実行する。

```sh

PYTHONPATH="$PWD/backend/src" python3 devel/measure_gui_api.py --prepare-fixture --profile populated
```

出力の `sqlite_path` の一時DBと `login_ids` を使用する（`synthetic-00` が講師、`synthetic-01`～`synthetic-24` がメンバー。パスワードは計測専用の `local-synthetic-fixture-only`）。既存のDBは指定しない。
前後それぞれのチェックアウトで、同じseedの別DBに対して例えば次のように起動する。

```sh

env -u CALIBOO_DATABASE_URL \
  CALIBOO_SQLITE_PATH=/出力された一時DB/fixture.db \
  CALIBOO_DEMO_SEED=false CALIBOO_AI_PROVIDER=manual CALIBOO_COOKIE_SECURE=false \
  PYTHONPATH="$PWD/backend/src" python3 -m uvicorn caliboo_api.main:app --host 127.0.0.1 --port 8000

# 端末2
cd frontend

```

ブラウザの外部通信を無効にした状態で、Viteが示すローカルURLを開く。AI実行、有料サービスへの接続、実データ、実運用サーバーは使わない。
比較元/改修後で同一の端末・ネットワーク・ブラウザ条件、役割、対象ID、操作順を保ち、各利用者は個別ブラウザセッションで実際の利用時と同様に操作する。

1. メンバーはログイン→ホーム→強み→課題一覧を通常の操作間隔で訪問し、講師はメンバー選択と処理待ちジョブ一覧を確認する。内容を読む間隔と既定の5秒更新はそのままにする。大量反復や短周期での自動リクエスト送信は行わない。
2. 初回はブラウザキャッシュを空にし、再訪は通常キャッシュで測る。各画面への操作開始から期待する表示完了までの時間、API通信時間、HTTPエラーを記録する。
3. 同じ通常業務時間帯での操作結果を前後で分け、各画面のp50/p95とエラー件数を比較する。講師が強みを承認してからメンバーの強み/ホームに反映される時間、他ユーザーのデータが表示されないことも確認する。
4. 画面を閉じ、ローカル検証サーバーを停止する。生成した合成データ専用の一時領域を破棄する。

人数分の実ブラウザを同時に操作できる環境がない場合は、逐次API計測結果と区別して同時25人の検証は未実施と記録する。

## 課題一覧のSQL絞り込み

今回は未変更。課題一覧のSQLは合成データの両規模で7件固定だが、メンバーごとの可視性をPython側で絞るため、populatedの課題全体324件のうち実際に表示するのは48件（約15%）。データ規模に対して余分な読出しがある。

比較元のサーバーp50はsmall 6.093 ms → populated 10.625 ms。再計測ではpopulatedの改修前/後の中央値が10.436/10.060 msと同程度であり、p95は同じコードでも大きく変動した。SQL絞り込みがユーザー体感を改善する十分な再現性のある根拠は得られていないため、#25との競合を避け、この段階では見送る。今後、同一端末での反復実測・SQLの処理時間や取得行数・大きい実用規模での再測定を行い、ボトルネックが明らかになった時点で可視性・講師/本人権限・順序を保ったSQL絞り込みを検討する。

## Valkeyの採否

今回は未採用。データ増加に伴うホーム・強みの追加SQLとジョブ一覧の追加SQLをキャッシュなしで減らせた。正式ビルドの初期JS gzip削減も達成した。一方、実時間の測定にはノイズがあり、キャッシュが必要なほどの同一読出しの反復やDB時間が主要な遅延原因であることは未確認。25人同時利用の応答時間目標を達成したという結論ではない。

導入すると本人・講師間での権限分離、承認/異動/提出後の失効、既定の5秒更新との整合性、運用監視が追加で必要になる。次に同時25人程度の通常操作をローカルで再測定し、バッチ読出し後でも繰返し読出しによるDB時間が支配的と確認できたとき、Valkeyの候補を再評価する。


## 追補: 25ブラウザセッションでの通常遷移と頻用ルートの再分割

### 合格基準

Astra仕様の比較条件に従い、初回改修（`8c99b70`）でのSQL一括化を維持したまま、頻用ルートの表示時間を再検証する。

- 25人規模の通常操作では、各操作のp95を250 ms以下にする。全遷移をまとめたp95だけでは、特定の画面の遅延を隠せるため、画面別に判定する。
- 小規模データでは、基準版より悪化する量は `max(15 ms, 基準版の15%)` 以下。画面の表示時間とAPIの処理時間を混同せず、それぞれの比較条件を記録する。
- 正式ビルドの初回ログインに必要なJS gzipバイト数を基準版から15%以上削減する。
- 認証、候補の可視性、講師権限、5秒更新、画面操作を保つ。ログイン処理には認証固有の時間があるため、通常画面遷移と分けて記録し、認証を弱めて短縮しない。

### 独立検証時の25ブラウザ結果（旧版の参考）

改修前の基準版と初回改修（`8c99b70`）は、同じ25名の合成DBでブラウザコンテキストを2秒以上の間隔で順番に開く従来法で比較した。メンバーの16名は強み、8名は課題一覧、講師1名は解析管理に移動した。

| 操作 | n | 改修前 p50/p95（ms） | 初回改修 p50/p95（ms） |
|---|---:|---:|---:|
| ログイン押下→ホーム | 25 | 223.5/314.4 | 232.3/420.8 |
| 強み（見出しまで） | 16 | 104.6/141.6 | 174.2/311.9 |
| 課題一覧（合成課題まで） | 8 | 136.25/310.0 | 144.55/175.8 |
| 解析管理（画面タイトル） | 1 | 91.2/91.2 | 138.6/138.6 |

25名全員が完了し、想定外のHTTP/JSエラーは両版ともなかった。しかし、全遷移のp95が250 ms以下でも初回改修の強みp95は311.9 msである。強みの基準は静的見出しであり、候補・学習行動の表示完了を測っていない。解析管理もデータ表示完了ではない。

### 頻用ルートの見直しとJS量

ログイン、ホーム、強みはメンバーの頻用導線のため静的読込とし、その他14ルートは個別に遅延読込する。初回ログインとホームの間、強みの初訪問で追加のルートchunkを待つ時間を減らす。

正式ビルドのJS gzip量を、同じ計測スクリプトで3版について算出した。

| 初回ログイン画面 | 190,719 | 107,486 | 147,422 |
| 認証済み状態で初回ホーム | 190,719 | 127,907 | 147,422 |

見直し後の初回ログイン必要JSは基準版から22.70%減少し、15%削減の目標は引き続き満たす（上限162,111 B）。初回改修より最初のHTMLが要求するJSは増えるが、ログイン→ホーム→強みを利用する際の累積量は9,654 B減る。

### 25ブラウザセッション比較の再現手順

ローカルの正式ビルド済みチェックアウト専用の `devel/measure_gui_browser.py` を追加した。外部URLや任意のエンドポイントへの接続指定はない。計測前に各チェックアウトで同じ依存を使い `cd frontend && npm run build` を行う。Pythonのbackend開発用依存、Playwright Python、ローカルChromiumを準備する（依存やブラウザのダウンロードを計測中には行わない）。

改修後のチェックアウトルートから次のように実行する。

```sh
# まず3セッションだけの動作確認
python3 devel/measure_gui_browser.py --label smoke --smoke > smoke.json

# それぞれの独立した正式ビルド済みチェックアウトを指定し、一つずつ実施
python3 devel/measure_gui_browser.py --source /比較元 --label before > before.json
python3 devel/measure_gui_browser.py --source /初回改修 --label stage1 > stage1.json
python3 devel/measure_gui_browser.py --source /見直し後 --label optimized > optimized.json
```

必要なら `--browser-executable /ローカルChromium` で同一ブラウザ実行ファイルを指定する。25名分の `populated` fixtureが既定であり、`--profile small` は同じ人数でデータ件数のみ小さくする。スクリプトの `--source` はHTMLの正式ビルドとCalibooのソースを持つローカルディレクトリだけを受け取る。版ごとに一時DB・一時ポートを新しく生成するため、実データや既存DBを使わない。
各版の測定は順番に行い、他のテストを並行実行しない。

- 25コンテキストは講師1・メンバー24。前節と同じ架空ユーザー・課題・候補・ジョブを用いる。ブラウザコンテキストごとにCookieが分離される。
- 冷間フェーズは各新規コンテキストについて、ログイン画面表示→ログイン→実データのあるホーム→対象画面を1回ずつ操作する。メンバーは強み16・課題8、講師は解析管理1と同じ内訳。各参加開始の間を2秒以上空け、開いたコンテキストは維持する。
- 25コンテキストを開き終えたら6秒待つ。各コンテキストを順番にホームへ戻し、2秒以上内容を読んでから前と同じ対象画面へ再訪する。次の参加者への切替も2秒以上空ける。既定の5秒自動更新は変更しない。
- 外部へのページリクエストを遮断し、ブラウザから許可される通信はその実行で起動したループバックのViteプレビューのみ。バックエンドのTCP/IP発信を遮断し、AIはmanual、既存のDB接続設定は解除する。使用可能メモリが1,500 MB未満（Linux）または予期しないAPI/JSエラー・サーバー停止で中止し、完了分と理由を記録する。
- ログインフォーム表示時間（ページURLへの移動から入力とボタンの表示まで）、ログイン押下からホームデータが表示される時間、従来の画面マーカーまでの時間、既知データの表示までの時間を分離する。強みは合成の強み候補・学習行動・配信課題、課題一覧は合成課題、解析管理は処理待ちジョブ・評価結果が実際に表示されたことを確認し、遷移に対応するAPI応答も待つ。
- テスト用ミドルウェアでAPIのサーバー処理時間・SQL数を応答ヘッダーに記録する。別途ブラウザのResource TimingからAPI/JSの通信時間・転送量を記録し、表示完了との違いを確認する。ログインPOSTとホームGET、強みGETと学習行動GETを個別に集計する。p50は中央値、p95はnearest-rank方式。

> [!NOTE]
> 本計測は1台のヘッドレスChromium上で25個の独立したセッションを保持し、通常の操作間隔で順番に画面を操作するものであり、25人が同時に多数回操作する試験ではない。再訪フェーズも既存の5秒更新と画面の可視性の制御に任せる。外部リクエスト遮断に使うPlaywrightのルーティングがHTTPキャッシュを無効にするため、冷間/再訪は通常のディスクHTTPキャッシュ比較ではなく、同じSPA文書でのモジュール評価済み・未評価の比較である。初回ログインは毎回新しいコンテキスト。JS gzip量は別の正式ビルド計測値を用いる。
>
> 実測環境: Python 3.12.14、Playwright 1.62.0、Chromium 158.0.8127.0、Node.js 24.22.3、FastAPI 0.141.1、SQLAlchemy 2.1.9、論理CPU 9。本機のメモリ・ブラウザ処理・ホスト負荷が実際のGUI所要時間に含まれる。

頻用ルート見直し後も、正式ビルドをViteプレビューとFastAPIで通常操作する18項目のブラウザ確認を再実施した。保護ルートに直接移動した未ログインユーザーのログイン復帰、メンバーの主なページ、講師管理ページ、候補承認前の非表示・承認後の強み/ホームへの更新、ログアウトは全項目成功した。34件のHTTP 200、1件の204、2件の想定された401以外のAPI応答・JSページエラーなし。外部のフォント/ライブラリ配信先への通信は遮断した。
