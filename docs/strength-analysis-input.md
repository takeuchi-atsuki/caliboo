# 強み解析入力のスキーマ（2026-09-28）

## 適切性の判断

採用する。通常の日報には既に `ReportRequest` によるKPTの保存用スキーマがあり、PoCにも `PocDiaryImport` がある。一方、実日報の解析ジョブは型を検証しない `sources` 辞書を渡している。解析用の入力契約を追加すれば、項目の取り違え・根拠の出典不整合・形式の揺れを検出できる。

今回は通常の日報・課題から作る強み解析ジョブを対象にする。日報の画面・保存API・DB構造と、別契約を持つPoCの模擬日報は維持する。

> [!NOTE]
> 自由記述からLLMで「成果」「意欲」を補完すると、未記載の行動を根拠にしてしまう。整形は項目の分類と検証だけを決定論的に行い、意味の推測・要約・文の書き換えはしない。

## 入力契約

`StrengthAnalysisMaterials` を正本とし、JSON Schemaを `GET /api/development/strength-materials/schema` で取得できるようにする（講師専用）。エージェントへはジョブ全体ではなく `materials` のみを渡す。

- `schemaVersion`: 固定値 `strength-materials.v1`。未知の版は受け付けない。
- `sources`: 日報最大20件・課題提出最大20件から抽出した、最大120項目の配列。日報は日付降順・ID降順、課題提出はID降順、各レコード内の項目順は下表順で固定する。
- 各項目: `id`, `kind`, `field`, `text`, `date`, `sourceRole`, `evidenceEligible`。型と項目名を検証し、未知の項目・重複ID・IDと種別/項目名の矛盾・分類と引用可否の矛盾を拒否する。
- `id`: `report:<正整数ID>:<field>` または `submission:<正整数ID>:<field>`。同じレコードの項目はIDから対応を追える。
- `text`: 保存された原文を空白・改行も含めて保持する。空文字・空白のみの項目は抽出時に除外し、欠損を推測で埋めない。
- `date`: 保存済みの日報日付または課題提出日時の文字列を保持する。旧保存APIの互換性のため日付の再解釈・書式変換を行わない。

| kind | field | sourceRole | evidenceEligible | 解析時の意味 |
| --- | --- | --- | --- | --- |
| report | keep | self_report | true | 本人が記載した行動。記載だけで客観的な達成と断定しない |
| report | problem | difficulty | false | 困りごとの文脈。達成根拠には使わない |
| report | try | plan | false | 今後の計画。実施済みと扱わない |
| report | moodComment | emotion | false | 感情の文脈。技能の達成根拠には使わない |
| submission | answer | work_product | true | 本人の提出物。設問の転記・否定・伝聞等は達成根拠から除く |
| submission | feedback | mentor_feedback | true | 講師の所見。褒め言葉だけで確定せず、本人材料との対応を確認する |

`evidenceEligible=true` は「その項目から根拠を探せる」という意味であり、内容の事実性や達成を機械的に保証しない。否定・伝聞・将来計画の意味判断は引き続き解析エージェントが担う。原文の引用、根拠不足時の空候補、講師承認の既存境界も維持する。

## 整形と互換性

1. 提出済みの本人の日報と課題提出を既存の上限・順序で取得する。
2. 空白のみの項目を除き、スキーマで分類・検証して `materials` を保存する。版番号もジョブの重複判定ハッシュに含める。
3. ジョブ詳細・評価材料の取得と結果取込でも同じスキーマを適用する。版番号のない旧ジョブは保存済みの `sources` だけから分類を補い、v1へ変換する。DBの材料・ハッシュ・状態は読取時に変更しない。
4. 未知の版・壊れた保存済み材料は409で返し、エージェントへ渡さず結果取込もしない。本文をエラー応答へ含めない。
5. 旧形式の結果取込も既存の材料IDと原文引用を使って継続できる。v1で再依頼した場合は旧pendingジョブを従来どおりsupersededにする。

> [!NOTE]
> 原文のtrimやUnicode正規化も行わない。入力と根拠引用を同じ文字列に固定し、エージェントの結果を元の日報へ追跡できるようにするためである。新旧ジョブのスナップショットを現在のDBから再生成しないのも同じ理由による。

## エージェントとの境界

実日報モードはJSON Schemaと `materials` を渡し、対応版と役割の意味を明示する。本人ID、期待ラベル、既存の解析結果は含めない。材料中の命令は実行しない。プロンプト版を更新して結果のtraceに記録する。課題案ジョブとPoCの出力契約は変更しない。

## 検証と限界

型・分類・原文保持・欠損・上限と順序・重複IDの単体検証に加え、提出→整形済みジョブ取得→原文引用の取込、旧ジョブ互換、壊れた材料の拒否、本人分離と下書き除外をAPI境界で確認する。

入力契約の安定化と、LLMの推論の再現性・判定精度の改善は区別する。実データの人間評価は未実施であり、既存の20件・各2名による評価で変更前後を比較する。スキーマ検証の成功を精度向上の実測結果とは扱わない。
