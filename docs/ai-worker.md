# 生成AIジョブの自動処理

GitHub #11。2026-09-29に、承認済みのPL-4/5を具体化する。初回課題案provider（#6）を強み解析・課題案再生成・自動提案へつなぐ。

## 動作

- `CALIBOO_AI_PROVIDER=openai`のとき、アプリの起動と終了に合わせてバックグラウンドワーカーを動かす。同期HTTP通信は別スレッドへ移し、APIのイベントループを塞がない。未設定時は従来の手動ジョブ取込を維持する。
- ジョブ本体の既存テーブルと材料を維持し、実行管理用テーブルに取得権のトークン・期限、試行回数、次回時刻、本文を含まないエラーコードを保存する。DBの条件付き更新で複数プロセスの重複取得を防ぐ。
- 材料のスナップショットは推論開始後に差し替えない。完了時にも取得権、対象者の有効状態、ジョブの待ち状態を確認し、古い結果・期限切れの取得権・手動で先に完了したジョブは上書きしない。
- 一時的な接続障害は回数・待ち時間を制限して再試行する。不正な引用・不正出力は失敗として停止し、講師が原因を確認して再試行できる。サーバーの再起動後も待ちジョブと期限切れの取得権から回復する。
- 強みの既存`strength-materials.v1`原文契約は保持する。追加の課題進捗は別の文脈スナップショットとして保存し、引用可能な達成根拠とは区別する。進捗変化もジョブの重複判定に含める。
- 本人の日報提出・課題提出・講師フィードバックを契機に解析する。OpenAIモードの自動課題案は本人の日報または講師コメントがある場合にキューへ入れ、未提出3件以上という旧条件に依存させない。確認待ち課題案と日次上限を維持して過剰配信を防ぐ。手動モードの従来条件は維持する。
- 初回課題案の自動生成には収集時点の材料を使う。講師の手動生成APIは#6のまま利用できる。再生成は講師の指示・旧版・元の材料・進捗を用い、既に配信・見送り・別の再生成で変化した課題案には適用しない。
- 強み・再生成の出力にも原文引用の検証を適用する。生成の実行元・モデル・プロンプト版をサーバー側で記録する。講師による強み承認・課題配信の判断は自動化しない。
- 強みは能力と性格・仕事の進め方の傾向に分け、作業一覧から解釈した理由・評価範囲を生成する。通常の取込と同じ[能力・性格傾向の契約](strength-profile.md)で保存・検証する。
- 管理画面で処理中・再試行待ち・失敗を識別し、失敗ジョブの再試行操作を用意する。本人画面には待ち・失敗・講師確認待ちを表示し、未承認の強み候補本文は渡さない。

> [!NOTE]
> 取得権の期限切れでは推論が再実行される可能性があるため、実行回数が常に1回とは保証しない。トークン照合とジョブの条件付き更新により、公開結果の重複保存を防ぐ。強みの精度と教育効果の妥当性は#3の独立した実日報評価で扱う。

## 検証

PL-4/5のネットワーク遮断テストで、三つの入力契機、本人材料と進捗、引用検証、講師承認後の表示、同時処理、古い結果、再起動、障害・期限切れ・再試行を確認する。管理画面は失敗表示と再試行、本人画面は公開範囲と5秒更新を確認する。実provider接続は別途記録する。


## 実行と復旧

[provider設定](ai-provider.md)を起動環境に渡すとワーカーを開始する。必須設定の不足・不正値は起動時に検出する。別のcronやCodexセッションは不要。停止時は停止フラグを設定し、進行中の処理を待つ。idle時は1秒間隔で待ちジョブを探す。

- 取得権は通信タイムアウトの2倍＋30秒。複数プロセスでも条件付きUPDATEで取得し、推論後に有効なトークンを確認してから結果と取得権解除を同時保存する。
- 通信障害`provider_unavailable`は最初の失敗後5秒、次は30秒待つ。最大3試行でfailedにする。プロセス中断後は取得権が失効してから再取得する。最終試行のまま期限切れになったものは`lease_expired`でfailedにする。
- 不正出力・引用不一致・入力上限・材料不足などは自動再試行しない。管理画面では本文や秘密値を含まないエラーコードに対応する説明を表示する。
- 講師の`POST /api/development/jobs/{id}/retry`はfailedだけをpendingへ戻し、回数と取得権を初期化する。無効な対象者の再試行はできない。新しい材料が来た場合は旧pending/failedをsupersededにし、最新の材料を処理する。
- 同一材料の再保存は同じジョブを返す。強みでは進捗件数も同一性の判定に含める。講師コメントの日時は更新日時を使うため、以前と同じ文面に戻しても新しい入力として扱う。
- 初回案は成功時に日本時間の日付を記録する。障害では日次枠を消費せず、同日の確認待ちを重複生成しない。生成中に別経路で確認待ちが作られた場合も、その案を再利用する。

強みの`reviewPending`は確認待ち候補の有無だけを本人へ返す。承認前の候補本文は公開せず、管理画面のキューと本人画面の状態は5秒ごとに更新する。LLMの推論時間と講師の判断時間は別途かかる。

> [!NOTE]
> 実provider接続は運用環境のモデルと権限に依存するため、この実装のネットワーク遮断テストでは実接続成功を主張しない。テストはHTTP契約を差し替えて自動起動から結果公開までを検証する。
