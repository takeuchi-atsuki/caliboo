# Caliboo｜想定質疑応答集
キャリブレーション型教育ツール｜経営層・管理職・情シス向け
2026年11月26日版（発表原稿 A・B 案、RC3 検証結果に対応）

**答え方の基本：結論 → 理由・根拠 → 次に確かめること。** まず20〜30秒で回答し、相手の反応に応じて補足する。★は特に優先して練習したい質問。

## 1. 経営層｜目的・価値・投資判断

### ★ Q01. なぜ、新人研修にCalibooが必要なのですか？
年間20〜25人の新人に対し、講師1人で一人ひとりの強みを見つけ、伸ばすのは容易ではありません。日報を提出するだけで終わらせず、強みの発見と次の挑戦につなげることで、3か月という貴重な研修期間を最大限に活用したいと考えています。

### ★ Q02. 「3ヶ月で新入社員を戦力化する」とは、具体的にどういう状態ですか？
配属初日から、一定の業務を自信を持って任せてもらえる状態です。全員に同じ能力や速度を求めるわけではありません。部門ごとに到達目標を定義し、本人が得意なことと、次に伸ばすべきことを把握できる状態を目指します。

### ★ Q03. 本当に3か月で戦力化できるのですか？
現時点では目標であり、達成を実証したわけではありません。到達目標までの期間、講師の準備・指導時間、配属後のOJT工数を測定し、現在の研修と比較します。効果が認められなければ改善し、無理に導入を進めません。

### Q04. 既存の日報や研修システムと何が違うのですか？
既存の日報は、実施内容や進捗を確認する機能が中心です。Calibooは記録から強みの候補とその根拠を見つけ、本人へ返し、次の挑戦と振り返りにつなげます。記録を育成のサイクルに変える点が特徴です。

### ★ Q05. 投資対効果はどのように考えていますか？
講師が日報を読み解く時間と、配属後に教える時間をどれだけ減らせるかを見ます。ただし、AI候補の確認・修正時間も含めて計測します。費用と教育効果の両面から、現行の研修より価値があるかを判断します。

### Q06. 既製品や単にChatGPTを利用するだけで十分ではないですか？
強みの抽出自体は既存AIでも可能です。Calibooは日報、根拠、講師の確認、本人の挑戦、振り返りを一つの流れとして扱えるように作っています。既製品との比較は必要ですが、自社の研修に合わせて調整できる点を重視しています。

## 2. 管理職｜教育・講師負担・公平性

### ★ Q07. 強みは具体的にどのようなものが出てくるのですか？
例えば「SQLが得意」「原因の切り分けが上手い」「相手の立場で作業を整理できる」といった、次の仕事に生かせる表現です。その下に日報から読み取った具体的な行動を根拠として整理します。

### ★ Q08. AIが間違った強みを出したらどうしますか？
AIの結果は候補として扱います。講師が原文の根拠を確認し、必要なら修正・見送りを行い、承認されたものだけを本人へ表示します。AIに判断を任せ切るのではなく、指導者の判断を支援する設計です。

### Q09. 強みが見つからない新人はどうなりますか？
記録が少ないだけで「強みがない」と判断しません。根拠が不足していれば無理に候補を出さず、日報や面談を通じて、次にどのような行動を試すかを考えます。成長の機会を狭めないことを大切にします。

### ★ Q10. 結局、講師の作業が増えませんか？
その可能性はあります。候補の確認・修正時間も含めて1件当たりの負担を測り、講師1人で20〜25人を継続して支援できるかを確かめます。根拠の薄い候補を減らし、講師が本人と向き合う時間を増やすことが目標です。

### Q11. 日報が苦手な新人や、記述量の差で不公平になりませんか？
日報だけで本人の能力を決めつけません。記述が少なければ根拠不足として扱い、成果物や講師の観察、本人の対話も活用することを検討します。強みの候補を人事評価や順位付けにそのまま使う想定はありません。

### Q12. AIへの依存で、自分で考えなくなるのではないですか？
次の挑戦を決め、実行し、結果を振り返る主体は本人です。AIには根拠をもとに気づきを得る役割を持たせ、本人がそれを受け取って考える設計です。

## 3. PoC・推進｜実現性と今後

### ★ Q13. 現在どこまでできていますか？
日報の作成・提出、強み候補の取り込み、講師承認、本人への表示、個別課題の配信、振り返りまで、合成データを使って実画面で動作を確認しています。実際の社員の日報に対するAIの精度や教育効果は未検証です。

### ★ Q14. 精度をどのように検証するのですか？
自分の権限で検証利用が許可されている日報を20件目標に集めます。先に私が所感と根拠を整理し、AI候補との一致、見落とし、根拠の妥当性を比較します。確認・修正時間も記録し、必要に応じて別の評価者による確認を検討します。

### Q15. 20件では少ないのではないですか？
20件は初期PoCの目標で、一般化できる件数という意味ではありません。まず候補の品質や指導への有用性、確認工数の傾向を見ます。対象の偏りも確認し、研修展開の判断には追加検証が必要と考えています。

### ★ Q16. 誰が推進するのですか？ 他部署の協力が必要ですか？
まず私自身が自分の権限で可能な検証を進めます。客先で得た生成AI活用やモニタリングの可視化のノウハウを生かしてきました。展開する段階で、部門および情シスと相談し、運用条件や責任分担を整理するつもりです。

### Q17. いつから導入できますか？
導入時期を先に決めるのではなく、まず実日報で根拠の妥当性と確認工数を確かめます。その結果が良ければ、展開先と利用条件を整理し、小規模な研修で試行します。具体的な時期は検証結果に基づき判断します。

### Q18. OJTや他部署への展開はどのように考えていますか？
将来は教材、課題、到達目標などを各部門に合わせて設定できる共通の枠組みにしたいです。配属前の業務体験にも展開する構想ですが、今回の日報は育成目的に限り、配属判断への利用は別途ルールを設計します。

## 4. 情シス｜コスト・技術・情報管理

### ★ Q19. 費用はどの程度かかりますか？
発表では、外部AIに直接接続する場合の仮見積もりを一人一回約29円としています。20〜25人、月20日、3か月、一日1回なら約3.48万〜4.35万円です。これは強み解析の費用のみで、実際のAPI費用、基盤、保守、講師の工数は今後確認します。

### Q20. もっと安いモデルや社内AIを利用できますか？
将来的な選択肢として考えています。品質が基準を満たすか、費用やデータ取り扱い条件を確認し、適切な接続先を選定します。現在は手動取り込みモードも備えており、アプリから外部AIに自動送信せず動作を確認できます。

### ★ Q21. 客先情報や個人情報が外部AIに漏れませんか？
PoCでは検証利用が許可されているデータだけを使い、原則として手動モードで進めます。外部AIを利用する場合は、送信が許可された範囲と方法に限定します。社内展開前には情シスと相談し、データの分類、接続先、保存期間、アクセス権を確認します。

### Q22. システムの構成と性能はどうなっていますか？
現在はReactとFastAPIを中心に構成し、ローカル試用ではSQLiteを利用しています。共有運用を見据えたPostgreSQLの移行・復元検証も行いました。25人規模の性能目標はまだ満たしていないため、同時利用を想定した追加試験が必要です。

### Q23. アクセス権限や運用管理はどうなっていますか？
本人と講師で利用できる機能を分け、本人向けの情報を本人の画面で扱う設計です。実運用に向けては認証方式、管理者権限、監査、バックアップ、復旧、運用体制を情シスと確認します。プロトタイプの機能検証と本番運用の保証は別です。

### Q24. AIが使えなくなったら研修が止まりませんか？
手動モードで記録や候補の取り込みを行えるため、AI接続に依存しない形でも試せます。外部AIを本番利用する段階では、利用停止時の運用や切り戻し手順も整理します。AIが使えなくても研修自体を継続できる設計を目指します。
