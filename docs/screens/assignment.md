# 課題演習画面

## 概要

講師が出した課題に新入社員がテキストで回答・提出し、講師がコメントでフィードバックする画面。

- パス: `/assignments`(一覧。講師は`?tab=proposals`で「AIの課題案」タブ)、`/assignments/:assignmentId`(詳細)、`/assignments/proposals/:proposalId`(課題案の確認、講師のみ)
- 実装: `frontend/src/features/assignment/AssignmentListPage.tsx`、`AssignmentDetailPage.tsx`、`AssignmentProposalPanel.tsx`、`AssignmentProposalPage.tsx`
- ロジック: `useAssignmentList`(一覧)、`useAssignmentDetail`(詳細)、`useAssignmentProposals`(課題案一覧・生成)、`useAssignmentProposalDetail`(課題案の確認・配信・見送り)フック
- API: `GET /api/assignments`、`GET/POST /api/assignments/{id}`系、`/api/assignment-proposals`系(詳細は`docs/api.md`参照)

!NOTE: 資格勉強クイズ(客観式・自動採点、`docs/screens/study.md`)とは明確に別機能として位置づけている。役割分担: クイズ=知識定着のための自己学習ツール、課題演習=講師が評価・フィードバックする研修カリキュラムの中核。

## ロール(新入社員/講師)

ログイン中のユーザーのロール(`docs/screens/login.md`「ロール」)によって、可能な操作と画面の構成が変わる。認可はサーバー側で行い、画面側はロールに応じて操作UIの出し分けだけを行う。

| 操作 | 新入社員(`member`) | 講師(`admin`) |
| --- | --- | --- |
| 課題一覧・詳細の閲覧 | 全員宛て+自分宛ての課題のみ可(状態は本人の提出に基づく) | 全課題可 |
| 課題の作成 | 不可(403) | 可 |
| 回答の提出 | 可(本人の提出のみ) | 不可(403) |
| 新入社員全員の提出一覧 | 不可(403) | 可 |
| フィードバック | 不可(403) | 可(新入社員ごと) |
| AIの課題案の生成・確認・配信・見送り | 不可(403) | 可 |

!NOTE: 一覧・詳細APIの`status`/`submission`は、ロールによらず常に「呼び出したユーザー本人の提出」を表す(講師には提出が無いため常に未提出/`null`になる)。ロールごとにレスポンスの形や意味を変えると、同じ項目を読む側がロールによる例外を意識する必要が生じるため、講師向けの情報は専用の提出一覧API(`GET /api/assignments/{id}/submissions`)に分けている。

## 構成要素

1. 一覧(`AssignmentListPage.tsx`): タイトル・状態・作成日の3列テーブル(`AssignmentTable.tsx`)。作成日時降順で表示する。講師のときは状態列を表示せず(講師本人の提出状態には意味が無いため)、代わりに「配信先」列(全員/対象の新入社員名)を表示し、ヘッダー右に「課題を作成」ボタンを表示する。新入社員のときは、自分宛ての課題のタイトルに「あなた向け」タグを付ける。講師のときは一覧の上に「配信中の課題」「AIの課題案(確認待ち件数)」のタブを表示する(後述「AIの課題案」)。
2. 課題作成ダイアログ(`AssignmentCreateDialog.tsx`): タイトル・課題文の2項目。講師のみ開ける。
3. 詳細(`AssignmentDetailPage.tsx`): 課題タイトル・課題文の下に、新入社員は回答セクション・フィードバックセクションを、講師は新入社員ごとの提出一覧を縦に並べる。自分宛ての課題で講師のひとこと(`messageForMember`)がある場合、新入社員には課題文の下に「この課題について · 講師より」を表示する。講師には配信先と「この課題について」(ある場合)を表示し、課題案から配信した課題なら元の課題案へのリンクを表示する。存在しない課題IDを指定した場合は一覧(`/assignments`)へリダイレクトする。
4. 回答セクション(新入社員のみ、`AssignmentSubmissionForm.tsx`): 状態が`reviewed`の場合は回答文を読み取り専用表示、それ以外は編集可能なテキストエリア+提出ボタン(`submitted`のときはボタン文言が「再提出する」になる)。
5. フィードバックセクション(新入社員のみ): フィードバック確定済み(`submission.feedbackComment`が存在)の場合のみ読み取り専用で表示する。
6. 提出一覧(講師のみ): 全員宛ての課題は新入社員全員(未提出者を含む、表示名順)、個人宛ての課題は対象の新入社員1人について、表示名・状態タグ・回答(未提出の場合は「まだ回答が提出されていません。」)・`AssignmentFeedbackForm.tsx`を並べる。フィードバック欄は状態が`not_submitted`のときは入力不可+理由文言、`reviewed`のときはボタン文言が「フィードバックを更新する」になり上書きできる。
7. タイトル・課題文・回答・コメントのいずれかが空欄の間は、対応するボタン(作成する/提出する/フィードバックを送る)が非活性になる。

## 状態設計

`not_submitted`(未提出) → `submitted`(レビュー待ち) → `reviewed`(フィードバック済み)の3状態。

!NOTE: 状態はDBの列として持たず、「提出行の有無」と「フィードバックコメントの有無」から導出する(`backend/src/caliboo_api/data/assignment_data.py`の`_resolve_status()`)。状態を列として持つと、提出・フィードバックの更新のたびに列を同期させる必要が生じ、更新漏れによる不整合の余地が生まれるため。

- `submitted`(フィードバック未確定)の間は、回答を何度でも上書き再提出できる(提出行は新入社員ごと・課題ごとに1件のまま、`answerText`と`submittedAt`のみ更新される)。
- `reviewed`(フィードバック確定後)の再提出は409エラーになり、UI上も提出ボタンを表示しない。フィードバック文が特定の回答文を前提に書かれているため、回答だけ後から差し替わるとコメントが的外れな状態で残ってしまうことを避けるため。
- フィードバックの上書き(誤字修正等)は`reviewed`状態でも可能(状態は`reviewed`のまま)。提出のロックとは非対称だが、フィードバックの上書きは後続の成果物(新入社員の次のアクション)を無効化しないため許容している。
- 未提出(`not_submitted`)の課題へのフィードバックは409エラーになり、UI上もフィードバック欄を無効化する。

!NOTE: 詳細画面をダイアログではなく別ルート(`/assignments/:assignmentId`)にしたのは、課題文・長文の回答入力・フィードバックという分量をダイアログに収めるのが窮屈であることに加え、URLで特定の課題を直接開けるようにして、新入社員と講師が同じ課題を指し示しやすくするため(日報履歴詳細のダイアログ化とは分量・用途が異なる判断)。課題作成のみダイアログにしたのは、入力項目がタイトル・課題文の2つだけの単発操作で完結するため。

## 配信先

課題は「全員宛て」か「個人宛て」。手動作成でも対象者を選択でき、課題案からの配信は個人宛てとなる。個人宛ての課題は対象の新入社員の一覧・詳細にのみ出て、他の新入社員が詳細・提出を開こうとすると404になる(存在自体を見せない)。

!NOTE: 配信先は課題側の`assignment_recipients`テーブル(行なし=全員宛て)で表し、課題案テーブルには持たせない。配信先は課題そのものの属性で、手動課題の個人宛て指定でも同じ仕組みを使うため。既存の`assignments`テーブルに列を足さないのは、マイグレーションが無く`create_all()`が既存テーブルへ列を追加しないため(新テーブルなら既存DBにも作られる)。

!NOTE: 他人宛て課題を403ではなく404にするのは、個人宛て課題は本人に合わせた内容(本人の日報の引用を含みうる)で、存在や件数を他の新入社員に知らせる必要がないため。

## AIの課題案(講師のみ)

新入社員ごとの日報(KPT+きもち)・課題の提出状況・講師フィードバックを分析して課題案を作り、講師が確認・編集してその新入社員1人に配信する(または見送る)。

!NOTE: 「AI生成→講師確認・編集→配信」のハイブリッド構成にしている。講師の確認を経ずに新入社員へ課題が届く事故を避けるため(強み可視化の強み候補生成、BACKLOG #3と同じ考え方)。

### 一覧タブ(`AssignmentProposalPanel.tsx`)

- 新入社員を選んで「課題案をつくる」を押すと課題案を生成し、その課題案の確認画面へ移る。確認待ちの課題案がある新入社員を選んだ場合は、新たに作らず既存の確認待ちを開く。
- 状態フィルタ(確認待ち/配信済み/見送り)で一覧を絞り込む。既定は確認待ち。タブと状態はURL(`?tab=proposals&status=`)に保持し、リロード後も維持する。
- 一覧には対象者・課題タイトル・ねらい・状態・作成日を表示する。

!NOTE: 初期仕様は講師の手動実行から開始した。現在は下記の「再生成・自動生成・点数」と「自動ワーカー」に従って提出イベントも扱う。

!NOTE: 確認待ちがある新入社員への生成を拒否せず既存の確認待ちを返すのは、二重押しや別タブからの操作でもエラーにせず、同じ新入社員に確認待ちが溜まらないようにするため。

### 課題案の確認画面(`AssignmentProposalPage.tsx`)

- 左: 配信する内容(タイトル・課題文・「この課題について」(新入社員へのひとこと、任意))。確認待ちの間は編集できる。タイトル・課題文が空の間は「配信する」を押せない。
- 右: ねらい、提案した理由、生成時点の状況(提出数・フィードバック数・未提出数・直近のきもち)、分析した材料(日報・講師フィードバックからの引用と日付)。
- 「配信する」「見送る」(理由は任意)は確認ダイアログを経て実行し、完了後は一覧タブへ戻る。
- 配信済み・見送りの課題案は読み取り専用で表示する。配信済みなら左側に実際に配信した内容(講師が編集した後のタイトル・課題文・「この課題について」)と配信した課題へのリンクを、見送りなら生成時の内容と見送りの理由を表示する。
- 配信・見送りの完了通知は、戻った先の一覧タブに表示する。処理済みで409になった場合は、課題案を再取得して最新の状態を表示する。

状態は`pending`(確認待ち) → `approved`(配信済み) / `rejected`(見送り)の3つ。確認待ち以外の課題案の配信・見送りは409になる。

!NOTE: 状態は列として持たず、配信した課題への参照(`assignment_id`)と判断日時(`decided_at`)から導出する(課題の状態設計と同じ理由)。課題案テーブルは生成時の内容を変えずに残し、講師が編集したかどうか(`edited`)は配信した課題の内容との比較で導出する。生成内容と講師の判断結果を後から見比べられるようにするため。

!NOTE: 新入社員には「AIが作った」ことを表示しない(既存課題APIにも由来を出さない)。講師が確認・編集した時点で講師の課題として扱うため。新入社員に見えるのは講師のひとこと(「この課題について · 講師より」)のみ。

### 生成のしくみ

既定の生成はルールベース生成器(`backend/src/caliboo_api/services/assignment_proposal/`)で行う。課題テンプレート集(報告の構成、SQL JOIN、指摘の受け止め、Git運用、会議・用語、ふりかえり)のキーワードを、対象の新入社員の直近の提出済み日報5件と、その新入社員の提出への講師フィードバックに照合し、最も点数の高いテーマを選ぶ。

- Problem・Try・講師フィードバックの一致は2点、Keep・きもちコメントの一致は1点。同点はテンプレート集の順。
- その新入社員に配信済み・見送り済みのテーマは選ばない。どのテーマにも一致しなければ、ふりかえりの汎用課題にする(ふりかえりは除外しない)。
- 一致した文を「分析した材料」として引用する(日付の新しい順、同じ日付ならProblem・Try・Keep・きもち・講師フィードバックの順)。直近5件のうち3件以上が「もやもや」「つかれた」なら気分の材料を、未提出の課題があれば進捗の材料を加える。
- 同じ入力なら同じ課題案になる(決定論的)。

!NOTE: 未設定時の初期生成は決定論的なルールベースを維持する。明示設定で外部生成providerを選べる（末尾の追加仕様参照）。上記のキーワード重み付けと決定論性はルールベースに適用する。講師の指示による再生成は、手動モードではCodex出力の取込、openaiモードでは自動ワーカーで処理する。

!NOTE: Problem・Try・講師フィードバックを重くするのは、つまずき・次の行動・講師から見た課題が「次に出すべき課題」に直結するため。Keep・きもちは補助的な手がかりとして軽く扱う。

## 通知表示

提出・フィードバック保存・課題作成の結果はMUIの`Alert`で表示する。挙動(5秒自動非表示・閉じるボタン)は日報画面(`docs/screens/report.md`)の`feedback`と同様だが、状態名は`notice`にしている。

!NOTE: この機能では「フィードバック」が講師コメント(ドメイン用語)を指すため、UI通知の意味で`feedback`という変数名を使うと読み手が混同する。そのため`useAssignmentList`/`useAssignmentDetail`では通知用の状態を`notice`と命名している。

提出・フィードバックの保存が失敗した場合(通常はUIの無効化により発生しないが、複数タブを開いている場合など)は、エラー通知を表示した上で詳細を再取得し画面を最新化する。日報画面が「対処が変わらない」として一律の文言にしているのに対し、ここでは「最新の状態を再読み込みします」という実際に取れる対処があるため、文言と挙動を変えている。

## 未実装・簡略化した点

- 定期バッチは設けず、手動生成と日報提出イベントによる自動生成を提供する。再生成は下記のエージェント方式。
- 手動課題は全員または有効な新入社員1名へ配信できる。
- 評価は必須コメントと任意の0〜100点。点数を空欄にして更新すると点数を解除する。
- 提出形式はテキスト記述のみ(画像・ファイル添付は無し)。
- 提出の下書き保存機能は無い(日報のような`draft`/`submitted`の区別が無く、提出ボタンを押した時点で即座に`submitted`扱いになる)。
- フィードバック確定後に新入社員が再提出して再レビューを受ける「再レビュー・ループ」は無い(ロックのみ)。
- 課題の期限・添付ファイルは無い。
- OJT実務タスクの進捗管理は対象外(研修期間のカリキュラム課題に限定)。

## 再生成・自動生成・点数（2026-09-28）

講師は確認待ちの課題案に「AIに調整を頼む」を入力して再生成を依頼できる。旧版・指示・生成元を履歴に保存し、Codexセッションでエージェント生成した結果を取り込む。配信/見送り済み、別の再生成で内容が変わった課題案には409を返し上書きしない。講師には生成元（ルールベース/エージェント）を表示する。

提出済み日報の保存時、本人の未提出課題が3件以上なら課題案を自動生成する。目安は日本時間で1人1日1回。既存の確認待ちがあれば再利用し、講師が配信を決める。手動課題も有効な新入社員を個人指定できる。フィードバック点数は任意の0〜100整数。講師の課題詳細タイトルには提出状態を表示せず、新入社員本人には表示する。

## パステルUI改善（2026-09-28）

一覧・詳細・課題案詳細に共通の可変ページ余白を適用する。ボタン・入力・ダイアログ・タブ・表は共通テーマに従う。課題詳細や課題案詳細でもナビの「課題」を現在地として表示する。作成・配信・提出・フィードバックの仕様は維持する。

共通仕様は [UI改善仕様](../ui-refresh.md) と [アーキテクチャ](../architecture.md) を参照。
## 初回の生成AI課題案（2026-09-29）

運用環境で`CALIBOO_AI_PROVIDER=openai`を選ぶと、日報・課題進捗・講師フィードバックを用いた生成AIの初回課題案を作る。画面の確認・編集・配信操作は従来と同じ。引用検証に失敗した案は表示・配信せず、生成失敗として再試行を案内する。未設定時は従来のルールベースを維持する。理由と入力上限、障害時の扱いは [生成AI provider仕様](../ai-provider.md) を参照。


## 自動ワーカー（2026-09-29）

上記の未提出3件以上・日報提出による生成条件はmanualモードに適用する。openaiモードでは日報提出・課題回答・講師コメントの保存を契機に、本人の日報または講師コメントがあれば初回課題案を非同期生成する。確認待ち案があるときと日本時間で同日に生成成功済みの場合は増やさない。提出の保存は推論終了を待たない。

講師指示による再生成も自動処理し、元資料の引用と旧版を検証する。処理中・失敗・再試行の操作はエージェント管理画面で確認する。初回・再生成とも配信は講師が判断する。詳細は [生成AIワーカー](../ai-worker.md) を参照。
