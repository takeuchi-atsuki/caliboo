# 生成AI providerの設定と検証

初回の個人別課題案、強み解析、課題案再生成、OJT回答、学習チャットに適用する。OJTは [部署資料と引用の仕様](grounded-ojt.md) に従い、選択部署の検索上位5件と本人の同部署の直近12発言を送る。アプリ起動中の自動処理と復旧は [生成AIワーカー](ai-worker.md) を参照。

## 設定

既定は`CALIBOO_AI_PROVIDER=manual`。初回課題案は従来のルールベース、強み・再生成はCodexセッションの取込、OJTは関連資料の抜粋、学習チャットは考え方を整理する問いかけを返し、外部APIを呼ばない。

| 環境変数 | 値・既定 | 用途 |
| --- | --- | --- |
| `CALIBOO_AI_PROVIDER` | `manual`（既定） / `openai` | 初回課題案の生成器・自動ワーカーの有効化 |
| `CALIBOO_AI_MODEL` | openai時に必須 | 利用可能なStructured Outputs対応モデルを運用側で指定 |
| `OPENAI_API_KEY` | openai時に必須 | サーバーの実行環境から取得する秘密値 |
| `CALIBOO_AI_TIMEOUT_SECONDS` | 30（1〜120の有限数） | 外部通信のタイムアウト秒数 |

起動環境のシークレット管理を使い、キーをソース、設定画面、DB、コマンド引数、共有ログに保存しない。設定ファイルをアプリが自動で読み込むことはない。実際に課題案を生成すると課金を伴う外部通信が起きるため、利用するモデル・権限・支出上限は運用側で設定する。

## 入出力と失敗時の動作

- OpenAI Responses APIの`text.format`でJSON Schemaを指定する。`store=false`、ツールなし。仕様は[公式Structured Outputsガイド](https://developers.openai.com/api/docs/guides/structured-outputs)を参照。
- 初回課題案は対象者の直近5件の提出日報・直近20件の講師フィードバック・本人の課題進捗件数・利用可能テーマだけを送信する。表示名、ログイン情報、他人の材料を入力に含めない。本文内に本人が記載した名前などは原文の一部として残る。
- 入力本文は命令として扱わないと指示し、モデルにファイル・ネットワーク・ツール操作を与えない。本文の意味まで機械的に正しいと保証するものではなく、講師の確認・編集・配信を必須とする。
- 送信材料はUTF-8で200KB以下、応答は1MB以下。上限超過では本文を切り詰めず失敗にする。出力の型、5〜480分の目安、テーマの許可、1〜10件の材料IDと原文引用を検証する。出典種別・日付・欄名は入力から復元し、モデルが作った出典を採用しない。
- provider応答型は送信する厳格なJSON Schemaと同じ必須項目と追加項目禁止を検証する。強み候補の`kind`・`summary`・`scopeNote`も省略できない（能力の説明・評価範囲は空文字でも可。仕事の進め方の場合は空文字不可）。入れ子の候補・引用の余分なキーも拒否する。旧形式のmanual取込には既存の既定値を適用し、この変更の対象としない。
- モデルが拒否・未完了・不正JSON・必須項目欠落・余分な項目・根拠不一致を返した場合、課題案を保存しない。講師の生成APIは503で再試行を案内する。再試行は講師の操作で行い、同一HTTP処理内では繰り返さない。LLM障害をルールベースの生成成功へ置き換えない。
- OpenAIモードでは日報・課題提出・講師コメントの保存後にジョブを登録し、バックグラウンドで解析する。失敗しても提出内容を保持し、生成成功まで同日の生成枠を消費しない。一時障害は自動再試行し、失敗停止後は講師が管理画面で再試行する。
- 強み解析は最大20日報・20提出の原文と課題進捗を送り、課題案再生成は元の材料・進捗・旧版・講師の調整指示を送る。強みは引用適格性と `(kind,skillCode)` の重複、性格・仕事の傾向では異なる2本人記録と判断理由・評価範囲の存在を検証する（[出力仕様](strength-profile.md)）。再生成は元資料のIDと引用を検証する。本人への自動承認・配信はしない。
- 生成が重なっても、確認待ちの判定とINSERTを同じSQL文にすることで、対象者の確認待ちを重複作成しない。既存の確認待ちは再生成せず返す。
- 配信済み・見送り済みテーマは除外する（既存の汎用ふりかえりテーマは再利用可）。初回案の`generator`にはprovider・設定モデル・プロンプト版を記録する。

> [!NOTE]
> 引用が入力中に存在することと、教育効果があることは別の検証事項である。LLMの出力を見た人間ラベルや合成データで、実日報評価（#3）の合格を代用しない。実provider接続と教育的妥当性は、このネットワーク遮断下の契約テストとは別に評価する。

## 検証の対応

ユーザー承認済みのPL-4/5/6およびSP-3に対応する。`test_llm.py`でHTTP入出力・秘密値・上限・拒否・障害、`test_llm_proposals.py`（単体）で材料選択・引用・テーマ・同時作成、同名の統合テストで確認待ち・配信・所有者分離・失敗後の再試行を検証する。実ネットワーク接続は行わない。

### #19 実接続前の合成予行・契約回帰

- 通常の合成予行: `test_ai_worker.py`（統合）はFastAPIのlifespanと実ワーカーを起動し、一時SQLite・合成の日報、課題提出、講師コメントから解析・引用・講師承認・本人限定配信までを確認する。`test_llm_proposals.py`、`test_grounded_ojt.py`、`test_study_chat.py`（統合）で初回課題案、OJT、公開問題付きチャットを、`test_ai_worker.py`で再生成も確認する。providerのHTTP応答は全て合成で差し替える。
- 契約の回帰テスト: `test_provider_contracts.py`（単体）は実際の送信スキーマを取り出し、5種類（強み・初回課題・再生成・OJT・学習チャット）の正常な模擬応答について、入れ子を含む必須キーと追加キー禁止の整合を確認する。各必須キーの個別欠落と各オブジェクトへの余分なキーの挿入を`invalid_output`として拒否する。旧manual形式の既定値も別途検証する。統合テストは実APIルートとワーカーを経由し、欠落等がある場合に保存・配信しないこと、チャットの再送・初回課題の再試行を確認する。
- 実モデル接続: この先行作業ではAPIキーや設定値を確認しておらず、実API呼び出しも未実施。実際のモデルがスキーマを受理し、実モデルの応答が利用できるか、ブラウザー上で承認結果が5秒＋通信時間で反映されるかの実接続時の確認は #19 に残る。実日報の妥当性は #3 で別途評価する。

再現はバックエンドディレクトリから`python3 -m pytest --disable-socket tests/unit/`と`python3 -m pytest --disable-socket tests/integration/`を実行する（試験では合成の設定値と外部HTTPのモック、一時DBを使用）。テストを実行する環境に実providerの秘密値を渡さない。API入口の合成予行と、通常のGUI操作による手動予行、実接続確認は異なる検証として記録する。

## 学習チャットの文脈

[学習チャット仕様](contextual-study-chat.md)に従い、現在の質問・タブ内の直近12発言・任意の公開問題文と選択肢を送る。画像は代替文だけで、画像URL・採点用正解・解説は取得・送信しない。180KBを超える場合は古い発言を丸ごと外し、各発言の原文は書き換えない。現在の質問・問題だけで共通送信上限を超えた場合は503とする。出力型と文字数を検証し、設定・通信・形式の失敗では入力を保って再送できる。モデルが問題文から推論する内容を採点結果とは扱わない。
