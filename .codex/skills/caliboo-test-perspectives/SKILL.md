## 使用する場面

仕様の追加・変更を伴う実装で、新しい総合テスト観点が必要になったとき、テストケースを作成する前に使う。

`docs/test-perspectives.md`が実践してきた運用(各節に「YYYY-MM-DD にユーザー承認済み」を明記する)を手順として明文化したもの。`AGENTS.md`が求める「テストケース作成前にテスト観点の承認を得る」を実行するための具体手順。

## 手順

1. 仕様書(`docs/screens/*.md`・`docs/api.md`・該当する場合は`example/*.md`)から、今回の変更で外部から観測できる振る舞いの観点を抽出する。既存の`docs/test-perspectives.md`と重複させない。
2. 抽出した観点をユーザーへ箇条書きで提示し、**この時点ではまだテストケース(コード)を書かない**。過不足の指摘を受けたら反映する。
3. 承認を得たら、`docs/test-perspectives.md`に「YYYY-MM-DD(今日の日付)にユーザー承認済み」を明記した節として追記する。既存の節(ホーム・日報KPT・OJT・強み解析PoC等)と同じ粒度・文体に揃える。
4. 承認済みの観点をもとに、テストケースを作成する。
   - APIをまたぐ結合的な振る舞い → `backend/tests/integration/test_flows.py`
   - 画面操作を伴う振る舞い → `docs/manual-test-cases.md`
5. 次を確認する:
   - [ ] 観点に対してテストケースの漏れがないこと(観点1件につき対応するテストが1件以上ある)
   - [ ] 仕様書に対して観点の漏れがないこと(仕様書に書かれた外部から観測できる振る舞いが、いずれかの観点でカバーされている)
   - [ ] 追加した統合テストが成功していること(`caliboo-test-check`のコマンドで確認する)

## 注意

- 観点承認は仕様書レベルの合意であり、実装の詳細(関数名・内部構造)には踏み込まない。
- 承認済み観点を変更する場合(仕様変更等)も、同じ手順を再度踏む(再承認を得る)。
